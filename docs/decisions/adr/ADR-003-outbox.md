# ADR-003. События через outbox

Статус: принято. Связано с D-07, TR-27, TR-29.

## Контекст

Статус перевода хранится в базе, события нужны в Kafka. Нельзя потерять событие о выполненном переводе и нельзя опубликовать событие о статусе, который не сохранился.

## Варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| Писать в базу и в Kafka по отдельности | Просто | Сбой между записями теряет событие или публикует несуществующий статус |
| CDC из журнала базы (например, Debezium) | Нет кода публикации, минимальная задержка | Отдельная инфраструктура, события повторяют структуру таблиц |
| Outbox: событие в той же транзакции, публикует отдельный relay | Атомарно, формат события — контракт, а не таблица | Задержка до секунд, relay может опубликовать дубль |

## Решение

Outbox и relay, который выбирает неопубликованные события и отправляет их в Kafka с ключом `transferId`. Позже relay можно заменить на CDC по той же таблице без изменений контракта.

## Последствия

- Дубли возможны, поэтому каждый потребитель дедуплицирует по `eventId` (требование в [AsyncAPI](../../api/asyncapi.yaml)).
- Перестановка при повторах relay возможна, поэтому у события есть `transferVersion`, финальный статус не откатывается.
- Relay выбирает события по порядковому номеру `seq`, а не по времени: время из `now()` — это начало транзакции, и у позднего изменения оно может оказаться раньше. Внутри одного перевода `seq` совпадает с порядком версий, потому что изменения перевода идут по очереди. `occurredAt` — момент самого изменения (`clock_timestamp()`).
- Лаг relay — метрика с алертом больше 30 с (NFR-08).
- Механизм проверен на PostgreSQL: событие появляется в той же транзакции, что и статус ([`ddl-checks.sql`](../../design/ddl-checks.sql)).
