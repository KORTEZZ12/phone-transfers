# Журнал решений

Продуктовые и ключевые архитектурные решения. Статусы: **предложено** — ждёт подтверждения, **принято**, **отклонено**. Все решения итерации 1 приняты. Подробный разбор вариантов — в ADR: [ADR-001](adr/ADR-001-sync-until-hold.md) для D-02, [ADR-002](adr/ADR-002-antifraud-fail-closed.md) для D-03, [ADR-004](adr/ADR-004-limit-reservation.md) для D-04, [ADR-003](adr/ADR-003-outbox.md) для D-07, [ADR-005](adr/ADR-005-continuation-tasks.md) для D-12, [ADR-006](adr/ADR-006-161fz-confirmation.md) для D-13.

| ID | Решение | Почему | Альтернативы | Статус |
|---|---|---|---|---|
| D-01 | Только переводы внутри банка. СБП и другие банки вне рамок, точка расширения — транзитный счёт | Внутренний перевод показывает все механики надёжности без внешнего контура НСПК | Сразу проектировать СБП | принято |
| D-02 | Создание перевода синхронное до блокировки средств, дальше асинхронное: ответ сразу со статусом «В обработке», итог — в статусе и пуше | Отказ по лимиту и остатку клиент видит сразу; медленный антифрод не держит запрос | Полностью синхронно: ждать антифрод и проводку в запросе. Полностью асинхронно: принять без холда | принято |
| D-03 | Если антифрод недоступен, перевод уходит на проверку и автоповтор (fail-closed) | Без проверки антифродом перевод не выполняется | Пропускать без проверки до порога суммы (fail-open) | принято |
| D-04 | В лимит входят незавершённые переводы, проверка и резерв лимита атомарны | Иначе лимит обходится параллельными запросами | Считать только выполненные | принято |
| D-05 | Перевод создаётся по токену получателя из поиска, а не по номеру | Деньги уходят тому, кого отправитель видел на экране, даже если номер переназначили | Перевод по номеру | принято |
| D-06 | Леджер на двойной записи, проводки неизменяемы, исправления — сторно | Баланс всегда воспроизводится из проводок, ошибки видны в истории | Баланс полем, которое обновляется | принято |
| D-07 | Статус и событие пишутся в одной транзакции (outbox), в Kafka события переносит отдельный процесс | Нельзя потерять событие и нельзя отправить событие о статусе, который не сохранился | Писать в базу и Kafka по отдельности (dual write); CDC из журнала базы | принято |
| D-08 | Ключ идемпотентности создаёт приложение на экране подтверждения. Ключ хранится вместе с переводом и уникален в пределах отправителя всегда, повтор распознаётся без срока | Только клиент знает, повтор это или новый перевод. Окно в 24 ч отвечало ошибкой на повтор уже выполненного перевода, и приложение создавало второй (ревью 0.2) | Ключ на сервере; окно повтора 24 ч (было до 0.3) | принято, пересмотрено в 0.3 |
| D-11 | Аренда обработки: перевод ведёт один участник не дольше P-14. Повтор в это время получает 409, после — продолжает обработку | В NEW повтор получал то 409, то «продолжить» без критерия выбора | Всегда 409 до регламентной проверки; всегда продолжать параллельно | принято |
| D-09 | Валютные переводы — только в одной валюте, без конвертации; лимиты по курсу ЦБ | Конвертация — отдельный продукт со своими курсами и рисками | Конвертация при переводе | принято |
| D-10 | Без комиссии | Комиссия не добавляет механик надёжности, только проводку | Комиссия сверх месячного порога | принято |
| D-12 | Каждый асинхронный шаг перевода — задача в той же транзакции, что и статус. Регламентная проверка — последняя линия | После 201 шаг вызывался «сразу после коммита»: при падении сервиса перевод зависал в HELD или CHECKING навсегда, а снятие холда держалось на проверке раз в 15 минут с инцидентом | Вызов после коммита и регламентная проверка; команды через брокер | принято |
| D-13 | Перевод с признаками мошенничества приостанавливается до подтверждения клиентом, после подтверждения — повторная сверка с базой ЦБ и, если нужно, отложенное исполнение. Отдельные статусы SUSPENDED и COOLING | В 0.2 решение принимал только сотрудник СБ, клиент мог лишь отменить, через 48 ч перевод отклонялся. Закон требует уведомить клиента и дать подтвердить, а подтверждённый перевод после приостановки исполнить | Только внутренняя ручная проверка (было до 0.3); явно исключить 161-ФЗ из рамок | принято, сроки — на согласование с комплаенсом |
| D-14 | Пуши по матрице «статус × адресат»: получателю — только COMPLETED. Дедупликация по паре «событие + адресат», collapse-key у пуша | В 0.2 пуш на любой финальный статус уходил и отправителю, и получателю: получатель-мошенник узнавал, что перевод отклонил антифрод. Дедупликация по одному eventId при двух адресатах давала дубль или потерю второго пуша | Пуши обоим на всё (было до 0.3); пуши только отправителю | принято |
| D-15 | Тот же ключ с другим телом после синхронного отказа: 422 `IDEMPOTENCY_KEY_REUSED` без `existingTransferId`; `GET` синхронно отклонённого запроса — 404 | Отказ по лимиту, остатку или счёту до холда не создаёт перевод как ресурс: в ресурсе такие причины не встречаются, событий нет. Ссылка на такой перевод вела бы к ответу вне контракта (находка F-1 итерации 3) | Показывать синхронно отклонённый перевод в ресурсе и расширить `RejectReason`; отвечать на такой повтор исходным отказом | принято |
| D-16 | Пуш FAILED — только у перевода, который не выполнился после холда. Перевод, закрытый из NEW, событий и пушей не даёт, итог клиент узнаёт повтором запроса | События начинаются с блокировки средств (TR-27, D-07). Матрица пушей обещала пуш на любой FAILED, а модель данных его не порождала (F-2) | Публиковать событие и для NEW → FAILED | принято |
| D-17 | Повторная сверка с базой ЦБ после подтверждения при недоступном антифроде: перевод остаётся в CHECKING, задача повторяется по TR-20, через P-12 — алерт | Из REVIEW нет пути в COOLING: сведения из базы ЦБ, пришедшие после подтверждения, потерялись бы, а клиент уже подтвердил перевод (F-5) | Уводить в REVIEW, как первичную проверку; добавить переход REVIEW → COOLING | принято с риском: пока антифрод не отвечает, подтверждённый перевод нельзя отменить, клиент видит «В обработке»; через P-12 — алерт по задаче, разбор по runbook |
| D-18 | Сверка: проводка по переводу относится к дню выполнения перевода; проводка у перевода в POSTING — предупреждение, а не инцидент | Леджер и сервис переводов — разные базы, на границе суток проводка и COMPLETED попадают в разные дни; ответ леджера может быть ещё не обработан (отказ 8). Без этого сверка давала бы ложные инциденты (F-6) | Сверять по дню проводки; сверять только закрытые сутки с задержкой | принято |
| D-19 | Нет заголовка `X-Device-Id` — 400 `VALIDATION_ERROR` с полем `X-Device-Id` в `errors` | Заголовок обязателен для антифрода, а отдельный код приложению не нужен: реакция та же, что на любую ошибку формата, — дефект приложения в лог и мониторинг (находка F-3 итерации 3) | Отдельный код `DEVICE_ID_REQUIRED`; принимать запрос без устройства и отдавать антифроду пустое поле | принято |
| D-20 | Валюта перевода не совпадает с валютой счёта списания — 400 `VALIDATION_ERROR` по полю `amount.currency` | Переводы только в одной валюте (TR-24, D-09). Приложение само предлагает счета в валюте получателя, поэтому несовпадение — ошибка приложения, а не ситуация клиента (F-4) | Отдельный код 422 с подсказкой счёта; конвертация | принято |
| D-21 | Сроки P-11 и P-20 держит база: после срока `guard_transfer` пропускает только отказ, подтверждение и отмена получают 409 с текущим статусом REJECTED, колбэк с решением по проверке — 200 и `applied: false` | Регламентная проверка приходит раз в P-08, и до 15 минут после срока клиент видел «Подтвердите до …» и мог подтвердить, а сотрудник — одобрить просроченную проверку (F-7) | Сроки только регламентной проверкой; считать срок по моменту запроса без перевода в REJECTED | принято |
| D-22 | В лимит поисков P-02 и P-03 входят все поиски, кроме повтора номера с действующим токеном, в том числе «не найден» и свой номер | Перебор номеров опасен как раз на ненайденных: если они не считаются, лимит не защищает от перебора (TR-03, F-8) | Считать только успешные поиски | принято |
