# Итерация 3: mock, тесты и сверка

Версия 0.4. В итерации 3 требования стали исполняемыми. Mock-сервер держит правила проекта, Postman-коллекция проходит таблицу отказов и критерии историй, SQL сверки находит расхождения в деньгах. Всё это CI запускает на каждый PR.

## Что и чем проверено

| Что | Где | Сколько |
|---|---|---|
| Mock-сервер с состоянием: правила, сбои, виртуальное время | [`mock/`](../../mock/README.md) | 7 операций публичного и внутреннего API, управляющий API для сбоев |
| Postman-коллекция по таблице отказов и историям | [`tests/postman`](../../tests/postman/phone-transfers.postman_collection.json), собирается из [`scenarios.mjs`](../../tests/postman/scenarios.mjs) | 11 папок, 296 запросов, около 700 проверок |
| Проверка каждого ответа по OpenAPI | общий скрипт коллекции, схемы из [`openapi.yaml`](../api/openapi.yaml) и [`internal-antifraud.yaml`](../api/internal-antifraud.yaml) | код ответа описан, тело по схеме, лишних полей нет, заголовки на месте |
| Проверка событий по AsyncAPI | папка «09 События, пуши и outbox» | полезная нагрузка по схеме [`asyncapi.yaml`](../api/asyncapi.yaml) |
| Параллельные запросы | [`tests/concurrency-check.mjs`](../../tests/concurrency-check.mjs) | отказы 1, 4, 20 |
| Ежедневная сверка и витрина для отчётности | [`reconciliation.sql`](../design/reconciliation.sql), [`reconciliation-checks.sql`](../design/reconciliation-checks.sql) | 15 проверок на PostgreSQL 16 |

Какая строка таблицы отказов, какое правило и какая история чем проверены, видно в [матрице покрытия](coverage.md). Её собирает сборщик коллекции, поэтому матрица не расходится со сценариями. Проверены все 30 строк таблицы отказов и все 7 историй: 29 строк — в коллекции, строка 20 — параллельными запросами к mock и нагрузочным тестом леджера на PostgreSQL. Из 38 правил вне коллекции два: TR-15 (неизменяемость проводок проверяет `ddl-checks.sql`) и TR-33 (комиссий нет, проверено ревью).

Проверка контракта — общий скрипт коллекции. Он перехватывает каждый ответ публичного API и сверяет его со спецификацией. У объектов запрещены незадокументированные поля, поэтому расхождение ловится в обе стороны: mock вернул лишнее или контракт что-то забыл описать. Чтобы убедиться, что проверка не пустая, я добавил в ответ mock лишнее поле и убрал заголовок `Location`, и прогон упал на каждом затронутом ответе.

## Как запустить

```bash
cd tests && npm ci && cd ..
MOCK_AUTO_TICK_MS=0 node mock/server.mjs &
npx --prefix tests newman run tests/postman/phone-transfers.postman_collection.json -e tests/postman/mock.postman_environment.json
node tests/concurrency-check.mjs
```

Коллекцию можно импортировать в Postman вместе с окружением `mock.postman_environment.json`. Руками её не правят: сценарии лежат в `scenarios.mjs`, после изменения нужно запустить `node tests/postman/build.mjs`. CI проверяет, что собранная коллекция и матрица покрытия совпадают с репозиторием.

```bash
cd docs/design
createdb pt_recon && psql -v ON_ERROR_STOP=1 -d pt_recon -f ddl.sql -f reconciliation.sql -f reconciliation-checks.sql
```

## Находки

Mock пришлось написать так, чтобы он отвечал на каждый запрос. На восьми местах требования ответа не давали. Решения по ним — D-15…D-22 в [журнале решений](../decisions/decision-log.md): все приняты. Все они уже применены в документах и mock, тесты фиксируют выбранное поведение. Если решение пересмотрят, упадёт конкретный тест.

| ID | Что не было определено | Как сейчас | Где поправлено |
|---|---|---|---|
| F-1 | Тот же ключ с другим телом после синхронного отказа. По контракту приходит 422 `IDEMPOTENCY_KEY_REUSED` с `existingTransferId`, но перевода как ресурса нет: отказ по лимиту или остатку в ресурсе перевода не встречается, а `RejectReason` не содержит `LIMIT_EXCEEDED`. `GET` по такому идентификатору нарушил бы контракт | `existingTransferId` не передаётся, `GET` синхронно отклонённого запроса — 404. Приложение показывает форму перевода и удаляет ключ. D-15 | [соглашения API](../api/README.md#идемпотентность), [OpenAPI](../api/openapi.yaml), [состояния экрана](../design/client-states.md) |
| F-2 | В матрице пушей у FAILED есть пуш, но перевод, закрытый регламентной проверкой из NEW, события не даёт: `emit_event` публикует только после холда (TR-27). Пуша нет, и это правильно, но матрица обещала обратное | FAILED из NEW проходит без события и пуша, итог клиент получает повтором запроса с тем же ключом. Пуш FAILED уходит только после холда. D-16 | [матрица пушей](../requirements/business-rules.md#пуши) |
| F-3 | Нет `X-Device-Id`: заголовок обязателен, а кода ошибки для него нет | 400 `VALIDATION_ERROR`, в `errors` поле `X-Device-Id`. D-19 | [каталог ошибок](../api/README.md#каталог-ошибок) |
| F-4 | Валюта перевода не совпадает с валютой счёта списания (TR-24): кода нет | 400 `VALIDATION_ERROR` по полю `amount.currency`. Это ошибка приложения: оно само предлагает счета в валюте получателя. D-20 | [каталог ошибок](../api/README.md#каталог-ошибок) |
| F-5 | Антифрод не ответил на повторную сверку после подтверждения клиентом: куда идёт перевод. По TR-20 — в REVIEW, но оттуда нет пути в COOLING, и сведения из базы ЦБ потерялись бы | Перевод остаётся в обработке, задача сверки повторяется с паузами TR-20, через P-12 — алерт. Принятый риск: отменить такой перевод нельзя. D-17 | [интеграция с антифродом](../integrations/antifraud.md#повторная-сверка-после-подтверждения) |
| F-6 | Сверка за день: проводка в 23:59:59 и COMPLETED в 00:00:00 дают два ложных расхождения подряд. Перевод в POSTING с уже сделанной проводкой (отказ 8) давал ложный инцидент | Проводка относится к дню выполнения перевода. Проводка у перевода в POSTING — предупреждение до следующей сверки. D-18 | [сверка](../design/reconciliation.md) |
| F-7 | Срок проверки P-11 и срок подтверждения P-20 применяет регламентная проверка раз в P-08. Значит, до 15 минут после срока клиент видит «Подтвердите до …», хотя «до» уже прошло, и может подтвердить | Срок держит база (`guard_transfer`) и mock при любом обращении к переводу: подтверждение после срока получает 409 и статус REJECTED. D-21 | [статусная модель](../design/transfer-states.md#переходы) |
| F-8 | Входят ли в лимит поисков P-02 и P-03 поиски, которые вернули «не найден» или «свой номер» | Входят все поиски, кроме повтора номера с действующим токеном. Иначе перебор номеров не ограничен как раз там, где он опасен: на ненайденных. D-22 | [TR-03](../requirements/business-rules.md#получатель) |

## Ретро итерации 3

| Что пошло не так | Что поменял в работе |
|---|---|

Два документа противоречили друг другу, и заметил я это только на прогоне | Тест сверяется с исполняемой моделью, а не с таблицей в документе. Расхождение — находка F-2, а не правка теста под результат |
| В первом прогоне упало 18 проверок, и почти все — из-за ошибок в самих тестах: токен получателя истекал после сдвига времени, query-параметры терялись при сборке URL. Ошибка mock была одна: управляющий метод не сериализовал сумму | Каждая папка начинается со сброса и не зависит от других; после долгого сдвига времени — новый поиск получателя |
| Postman шлёт запросы по одному, и отказы 1, 4 и 20 в нём проверялись бы последовательно, то есть не проверялись | Параллельные запросы — отдельный скрипт, CI запускает его рядом с коллекцией |
